# Nakeuri Foundry audit — 2026-09-03

## Executive verdict

Nakeuri is an unusually broad **Flutter-first, polyglot engineering control plane**. Its strongest inspected differentiation is not raw code generation; it is the combination of durable scheduling, risk routing, repository governance, cross-stack contracts, tamper-evident evidence, independent-review contracts and release controls.

The project is **architecturally advanced**, but the repository does not yet contain the external evidence required to call it better overall than current flagship systems. OpenHands has a more demonstrated local/container/remote agent runtime; the official Flutter stack remains the semantic and runtime authority for Flutter; Wingspan offers a focused parallel specialist workflow; Symphony offers a narrower but concrete issue-to-isolated-workspace daemon; and Antigravity exposes an actively supported agent CLI/sandbox surface. Nakeuri is broader in governance than those individual tools, but breadth of implemented contracts is not the same thing as superior task outcomes or production maturity.

## Audit scope and evidence classes

Inspected scope: 102 Python source modules (9,639 physical lines), 73 test modules, packaging, CLI/MCP surfaces, runtime providers, scheduler/lifecycle, Flutter and polyglot adapters, security/release policy, GitHub Actions and public documentation.

Evidence is classified as:

1. **Implemented** — source and a deterministic local test demonstrate a contract.
2. **Locally verified** — the behavior ran successfully on this Windows host.
3. **Environment-ready** — a CLI/configuration is present, but the target runtime was not exercised.
4. **Externally proven** — a real provider/device/release run is source-bound and independently attestable.

Only the first two levels were broadly available during this audit. The checkout has no `.git` metadata, so a repository commit fingerprint and source-bound certification could not be produced.

## Material defects repaired during the audit

| ID | Severity | Previous behavior | Repair |
|---|---|---|---|
| A-01 | High | Windows ledger locking inserted a blank sentinel into JSONL and broke verification | Moved locking to a binary companion lock file and added a no-blank-lines regression |
| A-02 | High | Assurance ZIP manifests stored Windows separators while ZIP members used POSIX separators | Normalized manifest/archive names with `as_posix()` and tested the lifecycle archive |
| A-03 | High | Generated PR/release workflows invoked JSON commands without `--ci`, so a reported failure could exit 0 | Added strict machine exit behavior; warning tolerance is now explicit via `--allow-gaps` |
| A-04 | High | MCP advertised a stale version and its OpenHands tool bypassed the unified provider policy | Bound MCP to package version and routed lifecycle tools through `UnifiedLifecycleExecutor` |
| A-05 | High | `verify_project` ran Flutter commands for non-Flutter repositories and polyglot support was largely planning-only | Detection now drives profile-aware native checks for each project surface |
| A-06 | High | Provider status could say `pass` with no executable provider; CLI presence could be promoted to live Kubernetes/Flutter proof | Readiness and empirical execution are now separate; unavailable providers return a partial status |
| A-07 | Medium | Documentation linked missing V4 filenames and reported stale versions/test counts | Links, version presentation and validation snapshots were corrected |
| A-08 | Medium | Linux-only CI could not catch the ledger/archive portability defects and MCP dependencies were never imported | Added Windows CI and an installed-dependency MCP import/version smoke job |

## Remaining high-priority gaps

1. **No controlled head-to-head benchmark.** The 500-item corpus and harness are a protocol, not evidence of 500 successful tasks. Run representative real tasks against Nakeuri and baselines from an identical commit, model policy, budget and machine class, then inject hidden acceptance tests.
2. **Kubernetes is not end to end.** The provider creates a hardened ephemeral Job and validates a structured result, but the controller does not yet upload/checkout the exact workspace or synchronize changes/artifacts back. A commit string in pod output is not sufficient proof.
3. **No live Flutter product trial.** Flutter/Dart executables were discoverable, but version/runtime probes did not complete reliably; Dart MCP, official skills, analyzer, Android/iOS devices, Patrol and store delivery were not exercised against a representative Flutter repository.
4. **No working external agent provider on this host.** OpenHands and Antigravity SDK/CLI execution were unavailable; Docker daemon access failed; Kubernetes was only CLI-ready. The provider contracts passed local tests, not live lifecycle trials.
5. **Release security is incomplete.** `gitleaks`, `osv-scanner`, `semgrep`, `trivy`, `syft` and `cosign` were unavailable. SBOM/provenance configuration is useful, but external scan/sign/verify evidence is still required.
6. **No distributed/production proof.** There is no multi-host partition/soak result, scheduler failover claim, production health rollout, rollback drill, or externally anchored release attestation.

## Important medium-priority gaps

- MCP policy functions are implemented and adversarially tested, but they are not yet a single mandatory middleware path around every live MCP call.
- CI runs unit/integration tests but does not enforce measured coverage, formatting/linting, static typing or a minimum mutation/behavioral quality signal.
- V3/V5 implementation scores predominantly test source/capability presence. Their claim boundaries are now honest, but they should gradually be replaced by black-box behavioral acceptance checks.
- Polyglot semantic graphs still rely substantially on portable parsing unless the authoritative language server is available and queried.
- The Kubernetes and remote result protocols need signed source identity, artifact transfer, cancellation, resumability and controller-observed usage.
- The repository is alpha software. Dependency resolution is range-based rather than locked for development/release reproduction, and the license file contains the short Apache notice rather than the complete license text.
- Several modules favor dense one-line Python. This reduces reviewability and makes security/control-flow auditing harder despite acceptable test behavior.

## Recommended 90-day proof roadmap

### Days 0–30 — prove the Flutter core

- Select one production-like Flutter app plus one Flutter/full-stack monorepo.
- Create 20–30 real change tasks spanning UI, state, networking, persistence, native integration, migration, security and regression repair.
- Compare official Flutter tooling alone, Wingspan, OpenHands and Nakeuri-wrapped execution where integration permits.
- Record hidden-test pass rate, first-pass success, regressions, elapsed time, tokens/cost and human interventions.
- Run Android emulator/physical-device and macOS/iOS compile/device evidence; source-bind every artifact.

### Days 31–60 — complete the execution fabric

- Implement immutable source checkout/upload and result/artifact synchronization for Kubernetes.
- Add cancellation, timeout, retry/idempotency, log streaming and signed provider-result envelopes.
- Exercise Docker, OpenHands remote and Kubernetes through the exact same lifecycle contract.
- Add crash/lease recovery and multi-worker contention scenarios using real processes, not only simulations.

### Days 61–90 — release and comparative proof

- Install and enforce the external scanner/SBOM/signing toolchain in release CI.
- Add coverage, Ruff, static typing and workflow linting without weakening existing gates.
- Run staged rollout/rollback drills and Android/iOS delivery preflights in non-production accounts.
- Expand the paired benchmark only after the pilot methodology is stable; report confidence intervals and failures, not just averages.
- Have an independent reviewer validate the benchmark setup, artifacts and conclusions before publishing a superiority claim.

## Validation snapshot after repairs

- 159/159 tests passed in one discovery run.
- 73/73 test modules passed in isolated Python processes.
- Repository self-audit and policy/link integrity checks passed.
- 23/23 GitHub Action references were pinned to full commit SHAs.
- 22/22 adversarial checks and 10/10 polyglot smoke checks passed.
- V5 implementation coverage: 33/33; V3 Target-10 implementation coverage: 99/99.
- External empirical status remains `not_yet_proven` for every live provider/device/release/benchmark item.

These checks validate the current local code state. They are not independent approval, production certification or evidence of overall peer superiority.
